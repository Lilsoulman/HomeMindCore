# HomeMind 产品总设计

> 全产品唯一产品事实来源。三端（Core 后端 / Web / 移动端）的功能、计划与接入均以此为准；每次沟通确认后的方向调整先更新本文，再同步三端计划。
> 接口字段与状态码以运行中的 Swagger 为准；跨端契约见 [api-integration.md](api-integration.md)。

## 一句话定位

HomeMind 是以"家庭"为数据与权限边界的**家庭 AI 智能体**：把日程、待办、家庭知识、设备、生活事务和 AI 执行统一到可确认、可追溯的工作流中，持续理解家庭上下文，在需要时主动开口，在授权时受控行动。

## 产品方向共识（2026-08-14 确认）

### 定位与卖点

- **主线**：家庭 AI 智能体（主动式家庭管家），不是智能家居系统、不是本地生活平台、不是 AI 玩具。
- **卖点 = AI 本身**：真实、好用的 AI；AI 玩具/陪伴/对话只是"AI 是家里一员"的一个面，不主打 AI 玩具叙事。
- **不做"打败米家"**：设备控制 80-90% 功能与米家重叠且不如其成熟——设备控制是"你有我也要有"的地基，不是打入理由。
- **纽带定位**：站在米家/美团/支付宝/快递100 等优秀产品**之上**，用家庭上下文在它们的交叉点产生**单一产品给不了的独家决策**（如"天气×日程×门窗=提前出门建议"）。信息经过 HomeMind 必须发生增值，否则只是传话筒。
- **商业模型**：硬件 + 本地服务（硬件销售占首年收入约 80%）中，AI 是让硬件溢价的理由，不是独立收费品；县域家庭为"装好的家 + 有人管 + AI 主动服务"买单，不为软件订阅买单。

### 管家功能矩阵（手脚 2，B41 起）

8 个完整闭环管家功能，每个验证"主动"的一个侧面，互不重复：

| # | 管家功能 | 验证侧面 | 切片 |
| --- | --- | --- | --- |
| 1 | 家庭财务管家 | 主动分析+省钱建议 | B41-B42（推进中） |
| 2 | 家庭周末出游管家 | 上下文→生活服务闭环 | B50（依赖 MTR-1a/1b） |
| 3 | 快递管家 | 主动发现+即时价值 | B44 |
| 4 | 家庭日程协同管家 | 跨成员交叉发现 | B46 |
| 5 | 家庭回忆管家 | 手脚升级为主动服务 | B47 |
| 6 | 宠物管家 | 长期关怀+补货预测 | B45 |
| 7 | 缴费管家 | 到期预防+不逾期 | B43 |
| 8 | 家庭健康关注管家 | 长期关怀+趋势发现 | B48-B49 |

健康画像数据源：自建画像（本地存储）+ 安诊儿/医院报告截图 PDF 导入（用户主动提供，非系统对接）；只记录、提醒、趋势，不做诊断。

### 打入功能策略（需求出发，不功能出发）

- **判据**：客户有强需求**主动来求**（像"我要吃饭"之于美团）+ 现状没人解决得好 + AI 能做差异。
- **第一候选 = 家庭财务**："我家钱花哪了、怎么省"是普世主动需求；记账 App 只记不省（已衰落）、支付宝无家庭视角、无"省下多少"的结果可见——"家庭视角 + 主动发现 + 省钱结果可见"当前无产品做。
- 省钱入口 → 后续接本地优惠/团购/补贴 → 商家增量入驻，商业闭环从财务打开。

### 数据获取现实（落地约束）

| 数据 | 自动化程度 | 现实 |
| --- | --- | --- |
| 快递 | ✅ 唯一全自动 | 快递100 官方 MCP |
| 日程/天气 | ✅ 自动 | 已有资产 |
| 财务 | ⚠️ 手动低频 | 支付宝/微信 CSV 导出（无开放 API） |
| 健康 | ❌ 手动 | 安诊儿/报告截图 PDF 导入 |
| 本地信息 | ⚠️ 半自动 | 高德 POI（黄页级）；优惠/活动无公开 API → CPS 联盟或人工收集 |

设计原则：不追求全自动，追求**最小摩擦组合**（快递自动 + 财务低频手动 + 对话沉淀自然）。

### 硬件策略（感知层优先）

- 钱花在**感知层**（人体存在/温湿度/门窗磁/水浸/插座功率/空气质量/睡眠带）——感知数据 × 管家矩阵 = 独有的理解层价值；控制层用 Zigbee 通用件补齐。
- 协调器已就位（EFR32MG21）；HA 部署在 Windows N100（Docker Desktop），从 ZHA 切换 **Zigbee2MQTT**（社区主流，趁设备数为 0 切换零成本）。
- 硬件数据 → HA → 未来 SmartHome Connector → 上下文引擎：作息（人体存在）、能耗（插座功率）、环境（温湿度）。
- 设备采购首推：Aqara（生态最全）+ SONOFF（插座功率计量）+ 宜家 TRÅDFRI（灯泡）；买前在 zigbee2mqtt.io 查兼容性。

### Home Assistant Connector 边界（2026-08-20 提前开发）

- HA 是唯一设备网关：HomeMind 通过 HA 官方 REST 与 WebSocket API 消费已配对实体，不直接访问 Zigbee 协调器、MQTT、厂商云或设备私钥。
- 首批只读/可控域为 `light`、`switch`、`climate`、`cover`、`sensor`、`binary_sensor`；门锁、摄像头、告警器和未映射域不进入自动执行，后续需单独风险评审。
- HA Long-Lived Access Token 仅在家庭级 Secret Vault 保存；HomeMind 客户端只看标准化空间、设备、能力、健康和确认结果，绝不看令牌、HA URL、原始实体 ID 或原始状态。
- 设备控制始终先确认后执行；HA 服务调用后以状态回读或事件订阅确认，依赖失效返回真实失败，不将“命令已发送”伪装为“状态已生效”。

### 借鉴迁移清单（WorkBuddy + Hermes Studio 拆解，2026-08-14）

**P0 高价值**：

| 功能 | 来源 | 迁移形态 |
| --- | --- | --- |
| 微信/IM 助理入口 | WorkBuddy | 扫码绑定 → 微信对话即管家入口（零安装触达全家）→ 确认卡推微信；App 是管理端，微信是使用端 |
| 专家团范式 | WorkBuddy | 角色契约（输入/输出/禁止动作）+ 共享产物层 + 三个必须人确认点；B50 出游管家按此设计 |
| 自动化任务引擎 | WorkBuddy | 定时调度 × Agent 理解 × 工具调用（不写代码）；五要素（触发/输入/Prompt/工作目录/验收）——"主动"的执行引擎 |
| 设备网络层 | Hermes Studio | 设备发现/配对审批流/远程终端/文件传输 → 家庭主机可远程运维 |
| 任务三模式交互 | 两者 | Ask（只读）/Craft（直接执行）/Plan（先计划后确认）→ 映射确认中心 L1/L2/L3 |

**P1 改造借鉴**：任务工作区隔离（Run 产物分目录防串用）、Skill 渐进式披露（三层加载防上下文爆炸）、MCP 正式支持（即插即用）、本地模型策略（Ollama 敏感数据本地推理）。

**P2 产品框架**：生活场景三分类（信息整理型/实时决策型/高风险型）、约束先行交互（≤8 问 → 两版草案 → 人确认）、交付物即传播。

**已排除**：Coding Agents 管理（开发者工具）、Theme 外观、完整 RBAC 管理页、MCP Prompts 原语。

### 已否决方向（避免重走弯路）

- ❌ 早晚汇报作为独立功能（聚合型日报=没用；"发现型"内容可作单场景主动消息）
- ❌ AI 玩具作为主打（一次性硬件吃灰；差异是"记忆在主机、设备只是皮肤"）
- ❌ 老人监测作为卖点（小米/萤石已做；余姚年轻人与长辈分住）
- ❌ 果篮管家等垂直场景方案（太窄）
- ❌ 纯软件订阅收费（县域付费意愿极低；硬件+服务才是现金流）

## 当前能力边界

| 领域 | 已有能力 | 明确不做或受限 |
| --- | --- | --- |
| 身份与家庭 | 注册登录、令牌刷新、成员/邀请/角色管理 | 路径中的 `homeId` 必须等于令牌家庭 |
| 个人效率 | 待办、日历、订阅、旅行计划时间线、收藏、个人专家 | iCal 外部拉取在白名单配置前保持禁用；旅行计划仅聚合已确认日历事件 |

| 智能家居 | 空间、设备、场景、自动化、确认执行 | 只暴露标准化视图，不暴露厂商凭据 |
| AI 与技能 | 专家、会话、运行、确认、剪辑/思维导图 | 高风险动作须确认；不向客户端暴露 Prompt 或本地路径 |

## 核心体验

1. 用户登录后进入 Dashboard，查看家庭概览、提醒和待确认事项。
2. 用户在任一领域创建事实数据或提出意图；系统生成建议、运行或确认卡。
3. 客户端展示影响范围和风险等级；用户确认后才执行受控动作。
4. 客户端轮询运行状态或刷新领域资源；结果与审计均归属当前家庭和用户。

## 家庭财务产品卡

### 用户目标

家庭管理者在不交出银行卡、支付账户或原始票据的前提下，导入本地账单、看清近期支出、管理周期缴费，并在到期前获得站内提醒。家庭成员可以查看共享财务概览；写入权限仍由 Core 决定。

### 交付范围

| 用户场景 | 产品结果 | 约束 |
| --- | --- | --- |
| 导入本地账单 | CSV 解析为家庭支出流水，重复行跳过并反馈数量 | 仅上传解析文本；不接银行/支付平台 |
| 查看支出 | 按日期、分类查看流水和 30 天默认汇总 | 金额均为正向支出；不支持收入、退款 |
| 发现风险 | 展示订阅、疑似重复扣款和高占比支出建议 | 建议只生成 L1 确认卡，不会执行任何动作 |
| 管理缴费 | 建立水电燃气等到期账户，登记已完成缴费 | 不保存账户号码；不发起或代替支付 |
| 到期与趋势 | 展示提前 3 天/1 天的站内提醒和年度缴费趋势 | 当前没有系统推送；数据以服务端结果为准 |

### 体验验收

- Web 可完成 CSV 预览、导入结果、流水筛选、汇总和年度趋势；移动端可快速建档、登记已缴和查看提醒。
- 同一家庭的重复账单导入不产生重复流水；同一缴费账户与到期日的重复登记明确提示冲突。
- `viewer` 可读不可写；任何非当前家庭的 `{homeId}` 均被服务端拒绝。
- 原始账单、票据图像、账户号码、第三方凭据和自动支付入口均不出现在功能或日志中。

## 产品原则

- 家庭隔离：令牌中的 `tenant_id` 是家庭边界，客户端不得把家庭 ID 当作可自由切换的参数。
- 先确认后执行：涉及设备控制、自动化、AI 动作和生活建议时，默认可解释、可确认、可撤回。
- 最小数据：只收集完成服务所需的数据；凭据、令牌、完整运单号、原始账单和证件原件不返回客户端。
- 真实状态：依赖未配置、不可用或失败时返回错误，禁止返回伪造成功结果。
- 双端一致：移动端负责高频个人与家庭操作；Web 负责同一能力的宽屏管理，不创建两套业务规则。

## 角色

`owner`、`admin`、`member`、`viewer` 四种角色由后端计算权限。前端可用角色做导航提示，但所有按钮与数据必须以 API 的 `403` 结果为最终判断；`owner/admin` 专有的成员治理不得仅靠前端隐藏。

## 成功标准

- 用户能在移动端或 Web 以同一账号完成同一家庭的核心任务。
- 任何写入、确认与异步运行均可定位到用户、家庭、状态和时间。
- 每个已上线页面都对应一个真实 API 流程、空态、加载态、权限态和失败态。
