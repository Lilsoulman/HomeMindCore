# NexusMind 后端开发计划

> **依据：** `NexusMind-Product-Master-Design.md`、`NexusMind-Backend-Development.md` 与 `D:\HomeMind\mobile\docs\main\NexusMind-Frontend-Development.md`。
> **计划性质：** V2.3 的当前实施快照，只维护已完成、下一步和最小验收；产品决策及变更历史以产品总设计为准。
> **最后更新：** 2026-08-07

## 执行与回写规则

- 后续后端开发必须严格按本计划的当前切片、依赖、优先级和最小验收执行；未经计划调整，不得跳过切片、改变实施顺序或以手工代码修改替代计划项。
- 每次实施完成、部分完成、受阻或验证失败后，都必须先回写本计划的当前状态、下一步、验收结果和未验证依赖；随后在同一变更中按 `计划 → 后端开发设计 → api-implementation.md` 的顺序同步调整 `NexusMind-Backend-Development.md`、将受影响的路由、错误码、权限策略、响应格式、状态机、Swagger 描述与未发布契约写入 `docs/api-implementation.md`，最后再同步 `NexusMind-Product-Master-Design.md` 中受影响的设计、约束和实施状态；任何与产品总设计冲突的内容仍须以产品总设计为准。
- 手工调整代码后，如出现 Bug、测试不通过或实现与既定契约不一致，也必须遵循同一闭环：先调整本计划，再按 `计划 → 后端开发设计 → api-implementation.md` 的顺序同步回写受影响的路由、错误码、权限、响应与状态机，最后同步 `NexusMind-Product-Master-Design.md`；不得只修代码而不更新计划、设计和 API 实现文档。
- 如问题需要改变产品范围、领域语义、风险规则或跨端契约，仍须先由产品总设计确认决策，再同步修订后端开发设计和本计划；计划不得覆盖产品总设计。
- 每个切片实施完成、验证通过并回写本计划及同步文档后，必须执行 Git 上传指令归档：
  ```bash
  git add -A
  git commit -m "feat: <切片标识> <一句话完成说明>"
  git push
  ```
  提交必须包含切片代码、计划回写与设计同步的全部变更，且必须在切换到下一切片前完成。

## 当前基线

- 已完成 V1 Connector 与 Smart Home 基线：JWT 租户隔离、空间/设备/能力/状态/场景读模型、Mock、Connector 安全配置、Home Assistant 发现与同步、家庭管家 Run、行动确认执行、Dashboard、自动化与同步队列。
- 已完成 Expert Files 与多专家团队编排：受控文件生命周期、团队版本冻结、成员权限交集、聚合视图和审计；外部效果始终复用 Run Action 的确认、幂等与审计链路。
- 当前范围为 V2.2 家庭管家增量收尾（B9-B14）与 V2.3 个人生活专家前置（B15-B17：探店翻牌、行程规划）。V2.3 版本语义已修订：个人生活专家作为 V2.3 新增产品能力推进，产品决策以产品总设计变更记录为准。
- 所有后续切片都必须从 JWT 推导 `tenant_id`，禁止客户端覆盖家庭归属；不返回凭据、厂商字段、Prompt 或模型思考链；风险等级取静态基线、用户偏好与运行时上下文中的最高值。
- 创作者中心本地 MCP Bridge 是受控本机开发工具，不是业务 Connector 或移动端能力：只经既有 API 显式同步到本地 SQLite，只读查询，不直连生产库、不新增 MySQL 迁移、不反向写入 API。其运行与敏感数据规则以 `docs/mcp-creator-center.md` 为准。
- V2.4 已确认家庭/个人 Connector 作用域与 Web 治理：复用 `users`/`tenants`/`tenant_members` 固定角色，新增 Connector scope、个人 owner 与 OAuth 会话；不实现可编辑 RBAC 或 API 路由表。

## 代码注释规范（强制要求，全量覆盖）

> 适用范围：`HomeMind.Common.Model`、`HomeMind.Common.IServices`、`HomeMind.Business.IServices`、`HomeMind.Business.Services`、`HomeMind.Common.IRepository`、`HomeMind.Common.Repository`、`HomeMind.Common.Infrastructure`、`HomeMind.Api` 及其后续新增工程中的所有源码文件，包括但不限于实体类、ViewModel/DTO、仓储、服务、控制器、Swagger 文档元数据、配置类与后台 Worker。

### 1. 强制原则

- **类必须注释**：所有 `public` / `internal` 实体类、ViewModel、DTO、请求/响应模型、配置类、Controller、Service、Repository、Worker、Middleware、Filter、Attribute 必须在声明前使用 `/// <summary>` 给出中文注释，说明其领域职责、归属模块、生命周期或关键不变量。
- **字段必须注释**：所有 `public` 属性 / 字段必须在声明前使用 `/// <summary>` 写出中文注释；私有但参与持久化、序列化、并发控制、加密、审计的字段也必须注释。`Key`、`ForeignKey`、`NotMapped` 等特性可保留，但不再替代 `<summary>`。
- **Swagger 字段必须注释**：所有进入 OpenAPI（请求体、响应体、查询参数、路由参数、Header）的字段必须在对应的 `ViewModel` / `Dto` / `*Request` / `*Response` / `*Query` 类型上同时具备：
  - `/// <summary>`：中文业务说明；
  - `/// <remarks>`（可选但推荐）：补充约束、单位、取值范围、示例、跨端语义；
  - 数据注解 `[Description]` / `[Display]`（中文）或 XML 文档注释，配合 Swashbuckle 注释过滤器输出到 Swagger UI，使 Swagger 上每个字段均显示中文说明；
  - 枚举成员使用 `[Description]` 标注中文含义，Swagger 文档生成器据此展开。
- **入参与方法必须注释**：
  - Controller 中每个 Action（方法）必须使用 `/// <summary>` 注明：HTTP 动词、路径、所需权限策略、归属租户来源、典型成功与失败响应、主要风险点；并在 XML 注释中以 `<param>` 描述每个入参的语义、单位、可空性、限制条件。
  - Service / Repository / Worker 中每个公开方法必须使用 `/// <summary>` 注明职责、关键不变量和异常类型；非平凡参数以 `<param>`、返回以 `<returns>`、可抛出的异常以 `<exception cref="...">` 描述。
  - 私有方法、局部函数若承担关键业务（鉴权、审计、幂等、加密、跨域）同样需要 `/// <summary>`。
- **枚举与常量必须注释**：每个枚举值、静态常量字段须以 `/// <summary>` 注明取值含义与合法使用场景；枚举容器本身亦需注释。
- **接口与实现均需注释**：接口方法除签名外必须以 `/// <summary>` 注明契约；实现类不得省略对接口语义的二次说明。
- **XML 文档生成开启**：所有上述工程必须在 `.csproj` 中保留（或新增）`<GenerateDocumentationFile>true</GenerateDocumentationFile>`；CI / `dotnet build` 必须以 `TreatWarningsAsErrors` 严格对待 `CS1591`（缺少 XML 注释的公开成员）。新增源码不得以 `#pragma warning disable CS1591` 等方式抑制。

### 2. 注释语言与风格

- **统一中文**：`summary` / `remarks` / `param` / `returns` 一律使用简体中文，避免在中文注释中夹带未翻译的英文术语。
- **简洁、面向契约**：注释描述"该字段是什么 / 何时被写入 / 谁会读取"，而非逐字翻译属性名；禁止在注释中复述字段类型、默认值、是否可空等编译器可推导的信息，除非该默认值是不变量。
- **避免臆测**：注释必须基于实际代码语义、领域规则或文档；不确定的字段在补注释时优先参考 `database/` 迁移、相关服务实现与 `docs/api-implementation.md`，不得凭直觉编写与产品语义不一致的说明。
- **不暴露凭据或内部路径**：注释中禁止出现明文密码、Token、Vault 路径、对象存储密钥、内部 IP、第三方 ID；与凭据相关的字段注释仅说明"已加密/不返回/由 Vault 托管"。

### 3. Swagger 输出约定

- 在 `HomeMind.Api` 启动配置中保留并完善 Swagger / Swashbuckle 注释过滤器（`XmlCommentsIncludingInheritDoc`、Schema 过滤器、Enum 描述等），将上述 XML 注释完整输出到 `/swagger`。
- 所有 DTO / ViewModel 的字段若存在枚举、字典、时间戳（UnixTime / ISO8601）、分页（`page`/`size`）、租户/家庭作用域等特殊语义，必须在 `remarks` 中显式说明，避免客户端按默认解读。
- 任何返回敏感凭据、厂商实体 ID、协议字段、内部对象键的字段，禁止出现在对外 DTO；如已存在于内部模型，对外 DTO 必须显式标注 `[JsonIgnore]` 且不暴露。

### 4. 验收与执行约束

- 代码评审（PR / merge request）必须把"全量注释 + Swagger 字段说明"作为阻塞项；任一公开类型或 Swagger 字段缺少中文说明均不得合入。
